# `results/` — the reference run behind the paper

Every table and figure in the paper is regenerated from the JSON files here. **No training is
needed to verify a number**: the figure and analysis scripts read this tree, and the values below
are the ones that appear in the manuscript.

**This tree is read-only in practice.** Drivers write to `runs/` instead (gitignored, absent on a
clean clone), so re-running an experiment cannot overwrite a published number. A reader's output
lands at the same relative path as ours:

    diff results/<experiment>/<key>.json runs/<experiment>/<key>.json

Set `OSCILLATOR_RESULTS` to move the read root — pointing it at `runs` regenerates the figures and
analyses from your own run. See the top-level `README.md`.

The tree mirrors the paper's structure — one directory per experiment, named for what it measures,
matching the driver directories at the repo root (`keyword_spotting/`, `sva/`, `language_modeling/`,
`convergence/`, `cost/`, `robustness/`, `theory/`). See the top-level `README.md` for the
paper → code map and `figures/README.md` for the figure scripts.

## File conventions

Result files are written by `training/harness.py::save_result`, which wraps each payload in a small
envelope:

| field | meaning |
|---|---|
| `exp` | the experiment name — **identical to this file's parent directory** |
| `key` | the run identifier — identical to the file's basename without `.json` |
| `git_hash` | the commit a run was produced at. Written by the harness on every new run; the published result files do not carry it, because the history they were produced against is not the published one |

The three files in `cost_operation_accounting/` are the one exception: there `exp` is a **count of
exponential evaluations** (a Table 7 quantity), not an experiment name. The name collides with the
envelope field; the payload sets it first, so the count is what is stored.

Checkpoints (`*.pt`) and `**/ckpt/` subdirectories are **not** tracked — they are regenerated by
training (see the top-level README). The config-G SVA checkpoints (`sva/checkpoints/`) and the
TinyStories demo checkpoint (`figures/lib/models/TS_d2.pt`) are the deliberate exceptions, because
Table 3 and Figures 4 and 5 depend on them directly.

Training runs were produced on Apple Silicon (MPS); the drivers also select CUDA or CPU when that
is what is available (`training/harness.py::pick_device`), and all analysis and figure scripts run
on CPU. Re-running may differ in the last decimal from non-deterministic floating-point reductions;
the results and conclusions reproduce, individual digits are not guaranteed bit-identical.

## `convergence/` — two producers, one seeded and one not

`TS_verify_adaptive.json` (Table 6, and the right panel of Figure 7) is produced by
`convergence/ts_convergence.py`, which draws its 5 initial conditions per oscillator from an
unseeded RNG. Re-running it gives values a little different from the committed ones every
time: the sample is 57,900 solves, so a converged fraction moves by roughly ±0.15 pp between
runs. Agreement at that scale is the experiment working, not a failure to reproduce.

`L6_ode_verify_extended.json` (the left panel of Figure 7) comes from
`convergence/ts_convergence_tmax.py`, which seeds at 42 and reproduces bit-for-bit.

Both need the TinyStories checkpoints, which are not distributed — with one exception: the
d_osc=2 checkpoint is the one shipped for Figure 5 (`figures/lib/models/TS_d2.pt`), so the
d_osc=2 row of Table 6 and the whole of Figure 7's left panel are verifiable from a clean
clone with no additional download:

```
python convergence/ts_convergence.py --d_osc 2
python convergence/ts_convergence_tmax.py
```

`ode_verification_v2.json` in the same directory is a Proposition 4 antipodal-geometry check
on WikiText-2 (`convergence/ode_verification.py`). No number in the paper comes from it.

## Files outside the per-experiment layout

Ten result files predate the per-experiment layout and are still read by current code, so they
stay where their readers expect them:

* `tinystories_d{2,8,32}_3seeds.json` and `wikitext2_d2_5seeds.json` (top level), and
  `lm/wikitext2_d{8,32}_5seeds.json` — the d_osc scaling inputs read by
  `language_modeling/dimension_scaling_analysis.py`, `wikitext_extrapolation.py`,
  `wikitext_extrapolation_stats.py` and `tinystories_extrapolation.py`. These feed the uniform
  re-analysis behind Table 4 and Figure 6.
* `lm/tinystories_d{2,8,32}_5seeds.json` — read by `lm_5pt_runs/scripts/aggregate_5pt.py`.
* `kws_p_ablation_lohe_3seeds.json` — read by `keyword_spotting/rank_vs_sharpening.py`.

The `p = 1` column of Table 5 is **not** taken from the `p1_*` files sitting beside the other
columns. `kws_readout_exponent/p1_s0.json` is a single seed at 88.8199 and
`lm_readout_exponent/d{2,8}_p1_s0.json` likewise; as the caption says, the `p = 1` column
reproduces the main-table values, so it comes from Tables 1 and 4 (five seeds each). Checking the
column against the single-seed file in the directory will not match.

`lm/` is also the output directory of `language_modeling/{position_offset,coupling_amplification,
head_scaling,sequential_init,sequential_init_rk45,sequential_init_L6a}.py`, and `lm_verified.json`
records a re-evaluation of the TinyStories checkpoints against their committed perplexities.

## Files that back a printed number without matching it literally

These four are read by no script, but each supplies a value the paper prints. Searching for the
printed literal does not find them, because what they contribute is a difference, a mean-plus-
spread, or a rounded figure rather than a stored number, so they are easy to mistake for redundant
aggregates.

* `lm/sequential_init_rk45_L6a.json` — the WikiText-2 d_osc=2 (L6a) sequential-initialization run.
  Its *gaps* against the analytic PPL are what appear in the text: 110.344773 − 110.215640 =
  **0.13 PPL** (random init, 5 seeds) and 110.254301 − 110.215640 = **0.04 PPL** (sequential init,
  1 seed). Produced by `language_modeling/sequential_init_L6a.py --seeds 0 1 2 3 4`. Note that
  `lm/sequential_init_rk45.json` is a *different* model (L5c, analytic PPL 118.95) and backs
  nothing.
* `sva_paper_final.json` — the config-G (d_ff=64) five-seed SVA evaluation. Supplies Table 8's
  d_ff=64 row (`mean_hard`/`std_hard`: 92.11 ± 7.87 and 97.38 ± 0.33) and the four oscillator cells
  of Table 3 (`attention_diagnostics_oscillator`: 0.20 ± 0.11, 0.08 ± 0.04, 0.26 ± 0.09,
  0.07 ± 0.04). Table 3's softmax cells are also in `sva_verb_attention/sva_softmax_misclass.json`
  (`table3_mean_attn`), but the oscillator cells are here only. Table 8's other four rows come from
  `sva/sva_arch_sweep_5seeds.json`, which has no config-G group.
* `sva_architecture_sweep/sva_5seeds.json` — the standard-architecture SVA comparison
  ($d_{model}$ = 64, 2 heads, 2 layers, $d_{ff}$ = 256), five seeds per mechanism. It is the source
  of the **98%** figure the paper states three times (the Table 2 caption, the body, and the
  appendix's "both softmax and oscillator reach 98% overall (5 seeds each)"): `all_mean` is 0.97915
  for softmax and 0.97985 for the oscillator. Nothing else in the tree records this architecture —
  the sweep's own config A is softmax only and at three seeds, so it cannot support a claim about
  both mechanisms at five. The file stores accuracies only; the architecture it corresponds to is
  the one named in the appendix, not a field in the file.
* `sva_configG_5seeds.json` — the raw per-seed accuracies behind the row above, so it can be
  recomputed rather than taken on trust. Recomputing from these (stored to 4 decimal places as
  fractions) gives 92.11 ± 7.87 and 97.38 ± 0.34; the printed 0.33 is the aggregate in
  `sva_paper_final.json`, computed before rounding.
